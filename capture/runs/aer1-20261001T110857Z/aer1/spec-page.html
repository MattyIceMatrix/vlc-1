AER-1 / AI AGENT EXECUTION RECEIPT

AER-1: the open draft for portable execution receipts

Canonical definition

An AI agent execution receipt is a verifiable record of one AI agent tool call. It identifies the execution, preserves the exact bytes used for its output commitment, records the tool and time, and gives a reviewer a public path to inspect what the execution system observed.

Defined by Brennan Zambo, creator of the AI agent execution receipt space.

Open draft/RFC - a proposal, not a finalized standard

AER-1 (AI Agent Execution Receipt) is the open draft specification for portable, verifiable execution receipts for AI agents. It defines the receipt vocabulary, canonical bytes, and independent verification, so any agent's work can be checked by anyone, anywhere.

Status and scope

AER-1 is an open draft/RFC. It is intended for discussion, implementation experiments, and interoperability feedback. It does not establish certification, registry membership, universal adoption, or a finalized standards status.

Canonical home: https://zambo.dev/aer-1 · Implementation: the live Zambo MCP and public /run/<uuid> receipt pages.

Abstract

An AI agent execution receipt is a public, persistent, independently checkable record of one specific agent tool call. It identifies the execution, records when it happened, preserves the canonical bytes used for the output commitment, names the tool and caller scope, and exposes the observed result through a stable public URL.

The receipt answers a narrow question: what did this system record for this execution? It does not prove an external business outcome that the system did not observe, and it does not turn a planned, blocked, or preview action into a completed execution.

Whole-job provenance classes

A whole job can combine actions performed by Zambo, actions observed through a gateway, and actions reported by another agent. Every timeline entry must name exactly one provenance class so verification never upgrades a report into an observation.

EXECUTED BY ZAMBO

Zambo ran the tool and recorded the returned result. The receipt can attest to that execution and its stored output commitment.

OBSERVED VIA GATEWAY

Zambo observed the action through an integrated gateway. The receipt attests to the gateway observation, not to facts beyond what the gateway returned.

LOGGED BY AGENT

An external agent reported the action through the journal. Zambo attests that the report was received, redacted, timestamped, and chained. Zambo does not claim it ran or observed the action.

Entries for one job form an append-only hash chain. A public /run/<job-id> or /run/<entry-id> page resolves the whole timeline and reports whether that visible chain verifies.

Core vocabulary

Receipt

A public record for one execution with a stable UUID, execution metadata, canonical bytes, and an output commitment.

Canonical bytes

The exact UTF-8 byte sequence used for the output hash. Verifiers must receive or reproduce the same bytes before comparing hashes.

Observed result

The result the implementation received and stored. A receipt reports observation, not an unsupported claim about the world.

Evidence

When upstream data was captured, the receipt can identify its source, request parameters, capture time, byte length, and evidence hash.

Minimal receipt shape

This is the smallest useful interoperable shape. Implementations may add fields, but additions should not make the core identity or verification fields ambiguous.

{
  "receipt_id": "UUID",
  "receipt_schema_version": "0.3",
  "created_at": "",
  "tool": {
    "name": "example_tool",
    "version": "4.0.0",
    "scope": "public"
  },
  "canonical_bytes": "<base64 of exact UTF-8 bytes>",
  "output_hash": "sha256:<digest of canonical bytes>",
  "verification_status": "verified",
  "public_url": "https://zambo.dev/run/<receipt_id>"
}

The template is illustrative. The examples below are live records from the Zambo receipt store, not template data.

Verification procedure

  1. Resolve the public receipt URL and confirm the receipt ID matches the requested execution.
  2. Read the exact canonical bytes or the representation needed to reproduce them.
  3. Compute SHA-256 over those bytes and compare it with output_hash.
  4. Review the tool, timestamp, caller scope, observed result, evidence, and anchor status separately.
  5. Report only what the stored observation supports.

Design rationale

AER-1 starts with a narrow record rather than a universal theory of agent behavior. An agent may call several tools, receive information from several providers, and hand work to another agent. A reviewer still needs a stable way to identify one execution, understand what the system observed, and check whether the published bytes match the stated commitment. The draft keeps those needs separate from claims about the outside world.

The vocabulary is intentionally small because interoperability fails when every implementation gives a different name to the same boundary. An identifier locates the record. A creation time orders it. A tool and caller scope identify the execution context. Canonical bytes and an output hash make the stored representation checkable. A result preview gives a human a useful first read without pretending that a preview is the entire source dataset.

Provenance is a separate design axis. A system can execute a tool itself, observe an action through an integrated gateway, or receive a report from another agent. Those cases can all be useful, but they do not support the same statement. AER-1 therefore treats provenance as part of the record rather than as a marketing label. A verifier should be able to tell which party performed the action and which party only recorded the report.

The draft also treats failure as a first-class outcome. A malformed request, unavailable provider, blocked permission, or waiting access step still has a useful execution boundary. Erasing that boundary and returning a successful-looking summary makes later review harder. A compatible implementation should preserve status and explain the recovery path when the work did not complete.

Field walkthrough with a live receipt

Use a public receipt such as the live live_price example above as the running case. First resolve its UUID and confirm that the public page, API response, and verifier request all use the same value. This protects against a common review error: copying a result from one record while checking the integrity state of another record.

Next inspect created_at, tool, and caller. The time tells you when the receipt store created the record. The tool tells you which capability crossed the execution boundary. Caller and session fields provide context when they are included. None of these fields alone proves that the returned market data was correct. They identify the record and its context so that the evidence can be evaluated at the right boundary.

Inspect job_summary, steps, and result_preview next. For a single tool call, the step list should show the tool and its recorded status. For a whole job, the list can explain the sequence without requiring a reviewer to reconstruct the original chat. A preview helps a person decide what to inspect, but it must not be treated as a complete copy of every upstream response or as a replacement for source evidence.

The integrity check uses canonical_bytes, canonical_byte_length, output_hash, and hash_algorithm. Fetch the representation that the implementation exposes, compute the declared digest over the exact bytes, and compare the result. If the bytes or algorithm are unavailable, report that verification is unavailable. Do not silently substitute a different serialization, whitespace policy, or JSON key order and call the result verified.

Evidence and provenance complete the review. Evidence fields identify an upstream source when the tool captured one, while provenance fields explain whether Zambo executed, observed, or logged the action. Anchor and check fields expose additional state when the record contains it. A valid integrity check means the stored bytes are stable. It does not mean that an external provider was accurate, that a trade settled, or that a business outcome occurred.

The running example therefore supports a precise statement: the named tool ran or was recorded at the stated time, the receipt store returned the stated result, and the public record can be checked through its verification path. It does not support a broader statement about every market, account, or external event. AER-1 is useful when that distinction is visible to the next reviewer.

Conformance notes

A conforming implementation should make the receipt identity stable, expose the schema version, preserve the exact bytes used for the output commitment, and state which hash algorithm produced the digest. It should return a clear status when required data is missing. It should not report a receipt as verified merely because a database row exists or because an agent supplied a confident summary.

Conformance also includes the negative space around the record. The implementation should distinguish an attempted action from a completed action, and an observed result from an assertion about the outside world. If a gateway only received a report, the receipt should say that it logged the report. If a provider was unavailable, the status should remain unavailable. If a human approval is required, the receipt should expose the waiting boundary rather than implying authorization.

Interoperability testing should use fixed examples and failure cases. A test vector can include a known UUID, canonical byte sequence, hash, expected status, and provenance class. The verifier can then check the positive case, a changed byte, a changed algorithm, a missing field, and a mismatched identifier. Public test vectors are valuable because another implementation can reproduce the checks without access to the original database.

Version compatibility requires care when fields are added. New optional fields should not change the meaning of existing identity or integrity fields. A verifier that cannot interpret a required version should fail clearly and preserve the distinction between unsupported and invalid. An old receipt should remain inspectable when the implementation can still interpret its schema, while a changed storage representation should not be presented as the original canonical bytes.

AER-1 does not define a certification program, a registry, a legal standard, or a guarantee that every implementation will use the same transport. It defines a proposed vocabulary and verification boundary. Implementers may expose the record over HTTP, a file, a message, or another transport, but the public handoff should still explain how a reviewer locates the record and checks the stated commitment.

Privacy and security considerations

Receipts should not publish credentials, private prompts, private contact details, or upstream response bodies that contain secrets. Public projections should redact sensitive fields while keeping the commitment and verification contract honest. Evidence hashes should remain distinct from transformed output hashes.

Integrity is not correctness. A valid hash shows that the stored canonical bytes match the stated commitment; it does not independently establish that an external provider's data was true or that a business outcome occurred.

Versioning and compatibility

Implementations should identify their receipt schema version and keep old receipts verifiable when the storage format evolves. A verifier should fail clearly when required bytes or metadata are unavailable rather than silently treating an incomplete record as verified.

How do executed and confirmed states differ?

A receipt with executed records that the execution boundary ran. A receipt can move to confirmed only after a real post-action read-back, callback, delivery event, or settlement is observed and bound to the record. A receipt without read-back evidence proves invocation, not effect.

Versioning and extensions

Extensions are additive and namespaced by their implementation. They must not alter the meaning of the core identity, byte, hash, provenance, or verification fields. A future AER-2 would be a separately identified proposal, not an automatic rewrite of AER-1. Verifiers should fail clearly on unsupported required versions.

Errata and feedback

Security considerations

Review replay, man in the middle, and denial of service risks separately. Replay requires identifier and freshness review. Man in the middle risks require HTTPS and byte comparison. Denial of service is an availability problem and must not be reported as a verification failure. Credential theft, provider truth, authorization, and business outcomes are out of scope.

Quantum-safe by construction: hash commitments, not signatures

AER-1 verifies with hashes, not signatures. A reviewer checks one receipt by recomputing SHA-256 over the exact canonical bytes and comparing the result with the recorded output_hash. A workflow is checked by recomputing the Merkle root over the ordered step outputs. The verification procedure has no signature step and needs no secret key material. Anyone can check a receipt with the public bytes alone.

This is a deliberate property, not an accident. Signature schemes face a migration problem: a signature issued today under a classical algorithm can be harvested now and forged later if the underlying math falls. Hash commitments have no such exposure. There is no encrypted payload to decrypt later and no signature to forge. A SHA-256 digest can only be matched by reproducing the exact input bytes, and reproducing those bytes is the check itself.

So AER-1's verification core needs no post-quantum migration. The receipt vocabulary, the canonical bytes, and the output commitment mean the same thing under any future algorithm landscape, because checking them depends on no algorithm that a quantum computer weakens. Should a future revision add an optional signature field, it would sit alongside the hash commitment, never replace it.

The remaining quantum consideration is Grover's algorithm, which halves the effective strength of a hash function: SHA-256 keeps 128 bits of effective preimage resistance. 128 bits remains far beyond practical attack. The posture is therefore durable by construction, not urgent by roadmap.
